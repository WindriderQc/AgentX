# Benchmark Thinking Extraction

This document explains the implementation of the `<think>` tag extraction and stripping in the AgentX benchmark system.

## Overview

Reasoning models (like DeepSeek-R1) often include an internal "thinking" or "reasoning" process in their response. In many cases, this process is enclosed in `<think>...</think>` tags (or sometimes just starting with `<think>` if truncated).

Including this thinking process in the response passed to the judge model can lead to:
1.  **Pointless Complexity**: The judge has to parse through a large amount of internal reasoning before finding the actual answer.
2.  **Increased Token Usage for Judges**: Passing thousands of "thinking" tokens to the judge model increases the cost and latency of the judging step.
3.  **Noisy Scoring**: Judge models might get confused by the reasoning process and score the model based on its "thoughts" rather than its final output.

## Implementation Details

### 1. Extraction Logic
The `extractResponse` helper in `src/helpers/ollamaResponseHandler.js` now detects `<think>` blocks in the model's output.

-   **Regex**: `/<think>([\s\S]*?)(?:<\/think>|$)/gi`
-   **Behavior**:
    -   All content inside `<think>` tags is extracted and moved to a separate `thinking` field.
    -   The tags and their content are removed from the main `content` field.
    -   If multiple `<think>` blocks exist, they are concatenated with double newlines.
    -   If the `thinking` field was already populated (e.g., by Ollama's native thinking extraction), the newly extracted content is prepended.

### 2. Data Storage
The `BenchmarkResult` model has been updated to include a `thinking` field.
-   `response`: Stores the "clean" answer (thinking process removed).
-   `thinking`: Stores the extracted reasoning process.
-   `tokens`: Continues to reflect the TOTAL tokens generated by the model (including thinking), as this represents the model's actual performance and cost.

### 3. Judging Process
In the benchmark execution (`src/services/benchmark/execution.js`), only the cleaned `response` is passed to the `scoreResponse` function. This ensures the judge only evaluates the final answer, leading to more accurate and efficient scoring.

## Impact on Benchmarks

-   **Latency/Speed**: Metrics like `latency` and `tokens_per_sec` still reflect the model's full execution.
-   **Quality**: Quality scores are now more representative of the model's ability to provide a correct final answer without being distracted by its internal reasoning process.
-   **Observability**: Users can still inspect the thinking process by checking the `thinking` field in the database or via the UI (if supported).
